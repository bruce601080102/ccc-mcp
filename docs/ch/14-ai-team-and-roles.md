# 14. AI 團隊、自訂工作流與自訂角色

專案頁上的「**AI 團隊與工作流**」卡片，是你決定新任務由誰做、依什麼順序、用哪個 AI 工具的地方。模型、推理等級、額度備援與審查關卡這些技術設定，預設都收起來，要用時再展開。本章說明這張卡片、如何建立自己的工作流與角色，以及無論你寫什麼都不會改變的部分。

## 1. 怎麼讀這張卡片

- **工作流。** 下拉選單分成「軟體開發團隊」（Classic、Standard、Full）、「日常團隊」（生活、商業、內容、決策）與「你自己的工作流」。選定後會列出**該工作流自己的步驟**，資料來自已儲存的工作流，不是固定範本：內容創作團隊會顯示助理、研究員、撰稿人、編輯與事實查核員，不會出現開發者。
- **步驟。** 每一列顯示步驟編號、角色名稱、AI 工具（ChatGPT、Codex 或 Claude Code）與「進階」按鈕。角色依顯示的順序執行。同一個角色出現兩次時只算一組設定，在第一次出現的步驟編輯。
- **儲存或捨棄。** 變更在按下「儲存」之前都只是草稿；有未儲存的變更時卡片會提示，開啟其他編輯器的按鈕也要等你儲存或捨棄。如果設定在別的視窗被改過，你的草稿會留在畫面上，並請你捨棄草稿以載入已儲存的設定，不會覆蓋另一邊的修改。
- **目標（Goal）。** 沒有開發者步驟的團隊會顯示提示：它可以執行一般任務，但目標階段需要開發者步驟（見第 6 節）。

新任務使用「任務開始當下」選定的工作流。任務會保留它啟動時的工作流與角色版本；之後再改卡片，不會影響已經在跑的任務。

## 2. 「進階」裡有什麼

| 位置 | 內容 |
| --- | --- |
| 步驟的「進階」 | 模型（選填）、推理等級，以及額度用完時改用的 AI 工具。自訂角色會開啟它自己的編輯器。 |
| 「團隊進階設定」 | 由誰挑新任務的工作流（選定的那條、任務協調者，或依任務文字）、兩個一鍵預設（所有內建角色都用 ChatGPT，或使用已安裝的 CLI 工具），以及審查關卡（對抗式審查強度、每個關卡的回合數 1 到 5、關卡放棄時怎麼處理）。 |

CLI 設定的是同一組值：`config role`、`config workflow`、`config workflow-selection`、`config review-gate`、`config profile`。見 [CLI 參考](8-cli-reference.md)。

## 3. 自訂工作流

按「新增工作流」（或對自己的工作流按「編輯」）：

1. 取個名字（最多 40 字）。
2. 加入步驟，最多 12 個，每步選一個內建或自己的角色。可以把步驟上移、下移或移除，「新增步驟」會在最後加一個。
3. 第一步必須是能產出成果的角色（分析師、設計師或開發者）；審查員檢查它前面做出來的東西。
4. 「儲存」。儲存後，這條工作流會成為新任務使用的工作流。

每個專案最多可有 20 條自己的工作流。內建工作流不能編輯或刪除，請另外新增。「刪除」只會移除你自己的：已在跑它的任務會繼續用，新任務改回 Classic 工作流。命令列上相同的操作是 `config workflow-save` 與 `config workflow-delete`。

## 4. 自訂角色

按「新增角色」（或在「管理自訂角色」底下按「編輯」）：

- **名稱**：最多 24 字，必須以文字或數字開頭，不能含 `< > & " ' \`` 或反斜線。
- **它的運作方式比照**：它所根據的內建角色，建立後不能更改。
- **指令**：最多 16,000 字，原文送出。
- **AI 工具**：自己的工具，或與它的基底角色相同。模型、推理等級與額度備援在「進階」。

每個專案最多 30 個自訂角色。角色不會被刪除：「停用」會保留所有版本，已經開始的任務也會繼續用它啟動時的那個角色。停用的角色不能加進工作流，仍使用它的工作流也不能開始新任務。

### 角色永遠做不到的事

自訂角色是「**名稱加上疊在某個內建角色之上的指令**」。凡是由程式碼強制的部分，都由內建角色決定：能不能改檔案、報告怎麼判定、跑在哪種 sandbox、是不是審查員。**你寫的任何文字都不能讓它多一項權限。**

| 規則的種類 | 誰寫的 | 你的指令能改嗎？ |
| --- | --- | --- |
| 你的指令 | 你 | 能 |
| 固定的執行契約（操作者政策、報告格式、交接與關卡規則） | ccc-mcp，有版本與 hash | 不能 |
| 程式碼強制的規則（讀寫權限、sandbox、計畫核准、專案授權、主機測試、關卡判定、額度備援） | ccc-mcp 程式碼 | 不能 |

這些內容會在同一則訊息中送給 provider。標記能讓結構清楚，但模型可能無視它們：這不是訊息之間的權限隔離，安全靠的是第三列。

## 5. 版本、釘住與匯入

- **版本。** 角色每次儲存都是一個不可更改的新版本，附 SHA-256 指紋。儲存時需要帶上你開始編輯的那個版本，所以兩個編輯者不會互相覆蓋。
- **釘住。** 任務開始一輪工作時，ccc-mcp 會把它用到的每個自訂角色凍結成快照（定義、基底角色、解析後的 provider 設定與固定契約清單）。之後編輯或停用角色，都不會改變那個任務；計畫核准也綁定被釘住的團隊。目標（Goal）也一樣：計畫會保留它寫成時的團隊，只有在變更之後才寫成的計畫會使用新的設定。
- **契約變更。** 任務被釘住時，如果 ccc-mcp 自己的固定契約改了，會先分類。只是措辭相同意思的調整，會被記錄，任務繼續。意思有變時，任務會在下一步之前停下，直到你在任務頁檢視並輸入指明該任務、步驟與契約的確認文字。專案的寫入授權不會替你接受它。
- **匯出與匯入。** 「匯出備份」與 `ccc-mcp project export` 會包含自訂角色、它們的版本、快照、名冊釘住，以及你的工作流所用到的角色。不包含每次執行所存的完整 provider 文字、另外儲存的 runtime API key 與可執行的 MCP server 登錄，若角色看起來含有憑證，匯出會直接拒絕。備份仍含有 Context、報告與任務歷史，請當作敏感檔案處理。
- **匯入時的信任。** 匯入的檔案視為不受信任的資料。裡面每個角色，不論檔案怎麼寫，都會以「等你確認」的狀態出現；在你確認之前，什麼都不能執行它、編輯它，或把它加進任務。專案頁的「等你確認的匯入角色」卡片會列出它們。「檢視並信任」會顯示它的來源、基底角色能做什麼與它的指令，並要求你輸入指明這個角色與版本的確認文字。ChatGPT、MCP 工具、worker、CLI 與專案的寫入授權都不能確認角色。

沒有自訂角色的備份仍以版本 1 寫出，舊版也讀得了。含角色紀錄的備份是版本 2，舊版會以「Unsupported project bundle version」拒絕，而不是只匯入一半專案。

## 6. 哪些團隊能執行目標

目標的一個階段，是靠主機對開發者所改內容跑的測試來驗收，失敗時也是把工作退回給開發者修正。因此只有含 `RD` 或 `SD/RD` 步驟的工作流能執行階段：Classic、Standard、Full，以及你自己、包含開發步驟的工作流（自訂角色以它所比照的內建角色計算）。日常團隊只寫報告、不改檔案，所以只能執行一般任務。

檢查發生在計畫儲存的時候。計畫若指定了沒有開發者步驟的團隊，或在選用其中之一時寫 `default`，會被拒絕並說明原因，不會等到你核准後才失敗。交付協調者（Delivery PM）會被告知哪些工作流能執行階段；團隊裡每個角色都用 Codex 或 Claude Code 時，不需要 ChatGPT 對話也能跑完。見 [15](15-goal-planner.md)、[16](16-phase-runner.md)、[17](17-goal-run.md)。

## 7. 已知限制

- 後端能建立「角色會收到什麼訊息」的預覽，也能對指令做關鍵字檢查，但這一版的控制台沒有顯示它們。檢查不給分數，「沒有發現」不代表安全。
- 部分匯入檢查的訊息由後端以英文寫成。
- 測試套件中的 Codex 與 Claude Code 是腳本化的 CLI；使用已安裝並登入的 CLI 的測試預設不執行。
- 角色 ID 由名稱產生（例如 `u-reviewer-one`），可讀但不能編輯。
