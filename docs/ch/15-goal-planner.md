# 15. Goal：規劃完整需求並核准計畫

**Goal** 是你只需提出一次的完整需求。Delivery PM 會把它規劃成多個階段（Phase）；你審閱計畫、要求修改，最後核准。規劃與核准**本身不會啟動任何工作**：不建立 Task、不派 Agent、不跑 Host Test、不修改你的檔案。一次執行一個已核准 Phase 的做法見[16. 執行一個 Phase](16-phase-runner.md)。

在本機主控台（`ccc-mcp ui`）專案側邊欄的 **目標** 使用，或用 `ccc-mcp goal ...`。英文版：[docs/en/15-goal-planner.md](../en/15-goal-planner.md)。

## 計畫包含什麼

階段數由 Delivery PM 依需求決定，沒有固定範本，只有 12 個的防失控上限。每個階段有範圍、交付內容、相依的階段（不可循環）、建議的工作流與風險，以及驗收條件。只有 `host_test` 與 `host_command` 由主機執行指令判定；`reviewer_check` 只是建議，`manual` 一定等待人工。指令是參數陣列，不是 shell 字串；計畫不得提出 commit、push、發佈、網路工具或其他修改儲存庫的動作。

模型回傳的一切都是**資料**。通過嚴格驗證（階段 ID 不重複、相依階段存在、無循環、大小有限、無機密）才會儲存，否則該次規劃顯示為失敗，且不儲存任何內容。

## Delivery PM

Delivery PM 是 **Codex 或 Claude Code CLI** 的一次唯讀執行，只在你要求時啟動。一次要求就是一次模型呼叫：沒有重試迴圈、每個 Goal 同時只能有一次進行中的規劃，且最多使用 10 次規劃。這裡無法啟動瀏覽器中的 ChatGPT；若專案的分析師是 ChatGPT 會明確告知，你可以改用 `ccc-mcp goal import` 匯入在別處寫好的計畫（會標示為手動）。真實 Agent 的規則與其他功能相同：專案需已授權，或設定 `CCC_MCP_ENABLE_REAL_AGENTS=1`。

## 狀態

| 狀態 | 意義 |
|---|---|
| 尚未規劃 | Goal 已建立，還沒有計畫 |
| 規劃中 | 有一次規劃正在進行 |
| 等待你核准 | 已有計畫，目前版本尚未核准 |
| 已核准 | 你已核准目前版本 |
| 已取消 | 最終狀態 |

狀態由已儲存的資料推導而來，不另外儲存，因此不會與資料矛盾。要求修改會建立**新版本**，先前的核准不會涵蓋它。

## 核准

核准是你在這台機器上的行為：互動式終端機（`ccc-mcp goal approve`），或在主控台輸入確認句 `APPROVE <goal> v<版本>`。核准綁定單一版本與其雜湊，記錄操作者、時間與當時的專案授權，重複核准不會改變任何東西。專案的 `--write` 授權絕不會替你核准計畫。**核准計畫不代表同意** commit、push、發佈、部署、提高權限、增加預算、信任不可信任的角色，或接受契約變更。

## 預算

計畫會宣告限制（每階段 3 次嘗試、20 次 Agent 執行、60 分鐘）。規劃本身不強制任何東西；執行 Phase 時由程式強制（見第 16 章）。計畫自己的 `enforced` 旗標固定為 `false`，計畫無法設定它。

## 儲存與限制

Goal 只存在 SQLite（`goals`、`goal_plan_versions`、`goal_plan_phases`、`goal_approvals`、`goal_events`、`goal_plan_runs`），只增不改，不寫入共用 Context。移除專案會一併移除其 Goal；清除任務歷史則不會。含有 Goal 的專案打包目前會被明確拒絕，而不是默默漏掉。

承接自 Host Test 修復的限制（執行 Phase 時會有影響）：沒有常駐執行器；被強制終止的測試子行程可能需要人工處理；Windows 尚未實測；網路檔案系統與兩台機器共用同一個目錄未涵蓋；舊版 ccc-mcp 混用時不受新租約完整保護。
