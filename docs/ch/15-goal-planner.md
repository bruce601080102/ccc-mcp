# 15. 任務與目標：對 ChatGPT 說，在同一處觀看

你在 ChatGPT 說出需求，ccc-mcp 安排 AI 團隊、在你的電腦上跑測試、審查、修正，直到完成或需要你做決定才停下來。控制台的**任務**頁顯示的，是 ChatGPT 讀寫的**同一批資料**。

## ChatGPT 判斷什麼、ccc-mcp 保證什麼

ChatGPT 負責分類每則訊息；不能依賴模型判斷的部分由伺服器強制執行。

| 你說的話 | ChatGPT 做什麼 | ccc-mcp 保證 |
|---|---|---|
| 一般問答、閒聊 | 直接回答，不建立任何東西 | — |
| 一次可完成的小修改 | `start_project_request`（單次任務，不建立 Goal） | 任務出現在「單次任務」 |
| 持續開發、多步驟、需要多輪測試與審查 | `start_goal`，附上它寫的簡短標題 | Goal 只會建立一次：相同 `request_key` 重試，或 Goal 仍未結束時重送相同需求，都會回傳原本的 Goal |
| 延續既有工作 | 先 `get_work_overview`，再對該 Goal 用 `plan_goal(change_request=...)` | 看起來像進行中 Goal 的新需求會回傳詢問（`needs_choice`），不會悄悄開第二份 |
| 專案不明確 | 詢問你 | 有多個專案卻沒指定時，不會寫入任何資料 |

只有工具結果說建立成功才算建立成功；ChatGPT 的口頭說法從來不是紀錄。這些工具與控制台讀寫同一份 SQLite 資料、套用同一套權限檢查。

## 工具

| 工具 | 讀／寫 | 用途 |
|---|---|---|
| `get_work_overview` | 讀 | 進行中的所有事：群組（Goal 與其步驟）與單次任務，含白話摘要、誰在做、進度、是否需要你 |
| `get_goal` | 讀 | 單一 Goal：計畫、核准、預算、每個步驟的 task（`evidence_reads`）、以及仍待你驗收的項目 |
| `request_goal_approval` | 讀 | 你要核准什麼、確認字串、在哪裡核准。它不會核准任何東西 |
| `start_goal` | 寫 | 開始追蹤工作；可選 `title`、`request_key`、`confirm_new`，以及 ChatGPT 寫的 `plan` |
| `plan_goal` | 寫 | 存入聊天中寫好的計畫，或請規劃者（Codex 或 Claude Code）撰寫／修訂 |
| `control_goal` | 寫 | `start`、`pause`、`resume`、`cancel`、`rename`。開始需要已核准的計畫、可寫入的專案與測試指令 |

唯讀 HTTP 連線不會提供寫入工具。長時間執行由 ccc-mcp 自己的執行服務負責，聊天結束後仍會繼續；ChatGPT 只能在你發話時回答，要看進度請問它或打開**任務**頁。

## 什麼需要你、什麼不需要

只有人能做的事才需要人：**核准**計畫（在這台電腦上輸入確認字串）、授予專案寫入權限、**驗收**測試無法判定的條件。已核准計畫內的一切自動進行：各步驟、host 測試、預算內的修正、審查、最終檢查。計畫或模型的任何說法都不能放寬權限、提高預算或自行核准。

## 任務頁

**任務**頁列出工作群組與單次任務。每個群組顯示白話摘要、誰在做、進度與「需要你」標記；展開可看各步驟，每一步連到記錄對話、host 測試與 diff 的 task。頁面原地更新：不會重新載入，你正在輸入的內容、捲動位置與展開狀態都會保留；斷線時畫面維持最後狀態並自動重試。

你也可以在頁面上方的輸入框描述工作，這會呼叫與 `start_goal` 相同的函式，並同時請設定好的規劃者（Codex 或 Claude Code）寫出計畫，你只需要閱讀並核准。核准對話框中「核准後立即開始執行」預設勾選：輸入一次確認字串，就核准該計畫版本並開始執行；取消勾選則只核准、不開始。

## 匯入的角色

自訂角色已不再於控制台建立。隨匯入備份而來的角色一律維持關閉。專案頁會顯示「等你確認的匯入角色」；「檢視並信任」會顯示角色、它的基礎角色（只有基礎角色決定它能做什麼）與來源，並且只有在你輸入該版本的確認字串時才會信任。MCP、CLI、worker 或專案的寫入授權都做不到這件事。

## Goal 的計畫與核准

**Goal** 是你只需提出一次的完整需求。Delivery PM 會把它規劃成多個階段（Phase）；你審閱計畫、要求修改，最後核准。規劃與核准**本身不會啟動任何工作**：不建立 Task、不派 Agent、不跑 Host Test、不修改你的檔案。一次執行一個已核准 Phase 的做法見[16. 執行一個 Phase](16-phase-runner.md)。

在本機主控台（`ccc-mcp ui`）從**任務**頁開啟 Goal，或用 `ccc-mcp goal ...`。英文版：[docs/en/15-goal-planner.md](../en/15-goal-planner.md)。

## 計畫包含什麼

階段數由 Delivery PM 依需求決定，沒有固定範本，只有 12 個的防失控上限。每個階段有範圍、交付內容、相依的階段（不可循環）、建議的工作流與風險，以及驗收條件。只有 `host_test` 與 `host_command` 由主機執行指令判定；`reviewer_check` 只是建議，`manual` 一定等待人工。指令是參數陣列，不是 shell 字串；計畫不得提出 commit、push、發佈、網路工具或其他修改儲存庫的動作。

若階段未指定工作流，或寫成 `workflow: "default"`，會使用「**AI 團隊與工作流**」選定的團隊。每一版計畫會保存執行順序、服務設定、審查關卡和已信任的自訂角色版本。修改團隊設定後，新計畫和新任務才會使用新版。階段只能在含有開發者步驟（`RD` 或 `SD/RD`，見[第 14 章](14-ai-team-and-roles.md#6-哪些團隊能執行目標)）的工作流上執行，所以計畫若指定其他團隊，或在選用其中之一時寫 `default`，儲存時就會被拒絕並說明原因。規劃者會被告知哪些工作流是 `goal_ready`。

模型回傳的一切都是**資料**。通過嚴格驗證（階段 ID 不重複、相依階段存在、無循環、大小有限、無機密）才會儲存，否則該次規劃顯示為失敗，且不儲存任何內容。

## Delivery PM

Delivery PM 是 **Codex 或 Claude Code CLI** 的一次唯讀執行，只在你要求時啟動。一次要求就是一次模型呼叫：沒有重試迴圈、每個 Goal 同時只能有一次進行中的規劃，且最多使用 10 次規劃。這裡無法啟動瀏覽器中的 ChatGPT；若專案的分析師是 ChatGPT 會明確告知，你可以改用 `ccc-mcp goal import` 匯入在別處寫好的計畫（會標示為手動）。真實 Agent 的規則與其他功能相同：專案需已授權，或設定 `CCC_MCP_ENABLE_REAL_AGENTS=1`。

## 狀態

| 狀態 | 意義 |
|---|---|
| 尚未規劃 | Goal 已建立，還沒有計畫 |
| 規劃中 | 有一次規劃正在進行 |
| 等待你核准 | 已有計畫，目前版本尚未核准 |
| 已核准 | 你已核准目前版本 |
| 已取消 | 最終狀態 |

狀態由已儲存的資料推導而來，不另外儲存，因此不會與資料矛盾。要求修改會建立**新版本**，先前的核准不會涵蓋它。

## 核准

核准是你在這台機器上的行為：互動式終端機（`ccc-mcp goal approve`），或在主控台輸入確認句 `APPROVE <goal> v<版本>`。核准綁定單一版本與其雜湊，記錄操作者、時間與當時的專案授權，重複核准不會改變任何東西。專案的 `--write` 授權絕不會替你核准計畫。**核准計畫不代表同意** commit、push、發佈、部署、提高權限、增加預算、信任不可信任的角色，或接受契約變更。

## 預算

計畫會宣告限制（每階段 3 次嘗試、20 次 Agent 執行、60 分鐘）。規劃本身不強制任何東西；執行 Phase 時由程式強制（見第 16 章）。計畫自己的 `enforced` 旗標固定為 `false`，計畫無法設定它。

## 儲存與限制

Goal 只存在 SQLite（`goals`、`goal_plan_versions`、`goal_plan_phases`、`goal_approvals`、`goal_events`、`goal_plan_runs`），只增不改，不寫入共用 Context。移除專案會一併移除其 Goal；清除任務歷史則不會。含有 Goal 的專案打包目前會被明確拒絕，而不是默默漏掉。

承接自 Host Test 修復的限制（執行 Phase 時會有影響）：沒有常駐執行器；被強制終止的測試子行程可能需要人工處理；Windows 尚未實測；網路檔案系統與兩台機器共用同一個目錄未涵蓋；舊版 ccc-mcp 混用時不受新租約完整保護。
