# 17. 執行整個 Goal：從核准的計畫到通過驗證的結果

Goal 的計畫核准後，你可以一次啟動來**執行整個 Goal**。Goal 執行會依相依關係允許的順序，一次一個替你啟動各個 Phase。每個 Phase 的執行方式如[第 16 章](16-phase-runner.md)所述（既有 Workflow 引擎裡的一個普通 Task、你的 Agent Studio 角色與 Provider、Review Gate、Host Test、Delivery PM 的修正迴圈）。某個 Phase 通過後，Goal 執行會把經過記錄下來、把下一個 Phase 需要的脈絡交給它、再啟動它。所有 Phase 都通過後，**會對整個專案重新測試**，才算 Goal 完成。

你不必再複製 Prompt、貼回結果，也不必手動建立下一階段的 Task。

使用方式：在 Goal 頁面按 **執行整個 Goal**，或執行 `ccc-mcp goal run GOAL-0001 [--wait]`。English：[docs/en/17-goal-run.md](../en/17-goal-run.md)。

## 誰讓它持續前進（說「自主」之前先讀這段）

它是**事件驅動，不是常駐服務**。每次有變化就會喚醒一個短命的 `ccc_mcp.goal_run_worker` 行程：某個 execution 結束、某個 Phase 改變狀態、或有人操作。Worker 取得 Goal 執行的檔案鎖、讀取已保存的狀態、做出下一個決定、行動；若期間又被喚醒（或自己這一步讓下一步成為可能）就再看一次，然後結束。

* **關閉瀏覽器不會有任何影響。** 這條鏈不經過瀏覽器。重新開啟頁面會看到同一份保存的狀態。
* **一個 Goal 執行同時只有一個監督者。** 第二個 worker 發現鎖被持有就離開；它帶來的喚醒會在第一個放手前被注意到。
* **如果所有行程都中止**（重新開機、`kill -9`），沒有任何東西會自己喚醒它。它會在 Web 控制台啟動、或控制台的 watchdog（每 20 秒）發現它安靜 60 秒時繼續，或由你執行 `ccc-mcp goal run-recover`。在那之前，Goal 執行只是在 SQLite 裡等著，並標示為 *stalled*。Watchdog 只喚醒，絕不替人回答該由人決定的問題。
* **在「Phase 1 通過」與「建立 Phase 2」之間當機，不會遺失也不會重複。** 記錄已通過的 Phase、建立下一個 Phase 的執行與它的 Task，每一步都可安全重做：下一次檢查會補上缺的，而一個 Phase 只可能有一個執行、一個 Task。
* **無法證明已消失的孤兒行程會讓 Goal 停止**，而不是重新派工。這沿用 Stage 0／B 的規則：被殺掉的行程留下的 Host Test 或 Provider CLI，只有在能證明正是記錄過的那一個時才會被停止，否則等人處理。

## 事前必須成立的條件

第 16 章對計畫中**每一個** Phase 的要求，並且在**任何東西開始前**就全部檢查，免得中途為了本來就能預知的原因停下：計畫版本由人核准（針對那個確切版本與雜湊）、專案已授權寫入、已明確設定測試指令、每個 Phase 的 Workflow 是有開發步驟的 Step Workflow、沒有角色需要 ChatGPT 瀏覽器分頁。一個專案同一時間只能跑一個 Goal（它們共用檔案）；Goal 執行擁有這個 Goal 時，也不能手動啟動 Phase。

## 發生什麼事

1. **依相依圖挑下一個 Phase**，不是依 Phase 編號。一次一個，所以兩個 Phase 不會同時改工作樹。
2. **透過 Stage B 的 Phase Runner 啟動**，使用固定的 Task ID（`GOAL-0001-P2`）。重複啟動同一個 Phase 只會回傳第一個執行，不會重複建立任何東西。
3. **把前面 Phase 的脈絡交給它。** Phase 通過時，Goal 執行會（只增不改、附雜湊）記錄：Task、每個角色的 execution 與其 Provider 和 Prompt 雜湊、各次嘗試如何失敗、Delivery PM 的診斷、Host Test（指令、結果、git revision）、檔案、以及工作樹的指紋。下一個 Phase 的 Task 需求會帶上一份有長度上限的摘要：交付了什麼、改了哪些檔案、如何驗證、過程中出過什麼問題。這只是參考資料，不能改變該 Phase 的範圍或驗收條件。
4. **某個 Phase 失敗、超過上限或需要人，整個 Goal 就停止。** 依賴它的 Phase 不會啟動。原因會用白話寫在頁面上。
5. **所有 Phase 通過後，驗證整個 Goal**（見下一節）。

## 最終驗證

「每個 Phase 都顯示 PASSED」並不夠。設定好的測試指令會在**整個專案**上於主機重新執行，並經過 Stage 0 的 Host Test session（與任何其他測試互斥，被中斷的測試會被辨識出來）。前後還有這些檢查：

| 檢查 | 失敗代表 |
|---|---|
| 設定的指令在整個專案上通過，沒有因「未收集到測試」、被中斷或被阻擋 | Goal **沒有**通過 |
| 最終驗收條件中，指令就是設定指令的，由這次執行驗證；其他條件需要**你** | Goal 等你輸入確認字串驗收（`ACCEPT GOAL-0001`） |
| 檔案與最後一個 Phase 留下的完全一樣（指紋） | 測試通過還不夠：由你決定 |
| 每個被變更的檔案都有某個 Phase 回報過 | 由你決定 |
| 沒有受保護檔案（git、ccc-mcp、CI、測試設定）與上次 commit 不同 | 由你決定 |
| Phase 回報過的測試檔案仍然存在 | 由你決定 |
| 任何 Phase 的 Task 都沒有未解決的審查意見 | 由你決定 |
| 沒有 Phase 是在人確認受保護路徑變更之後才繼續的 | 由你決定 |

模型說「做完了」永遠不算證據。這些檢查只會讓通過需要你，絕不會把失敗變成通過。

### 最終驗證失敗時

* **一般實作問題**在 Phase 內由第 16 章的修正迴圈處理，Phase 才能通過。
* **跨 Phase 問題**（每個 Phase 都通過、整體卻失敗）會有**一次整合修正**（`INT-1`）：用同一套機制執行、可追溯，以驗證的失敗輸出作為需求。它不能改寫已完成 Phase 的紀錄、驗收條件或計畫。之後最終驗證會再跑一次。它的嘗試與派工計入同一個 Goal 預算。
* **需求或架構的變更**不能由模型決定。若 Delivery PM 說這個失敗無法在核准的範圍內修好，或整合修正沒有幫助，Goal 會等你。**請 Delivery PM 擬修訂計畫**會產生一個*新的、未核准的版本*；在你讀過並核准那個確切版本前，什麼都不會繼續。只有在已通過的 Phase 完全沒變、且沒通過就結束的 Phase 改用新 id 時，執行才會依新版繼續（Phase id 一旦跑過就用掉了）。
* **無法安全確認**（不安全的 Host Test 殘留、被阻擋的環境、沒有進步）會讓 Goal 停止並說明原因。

## 哪些證據決定哪個驗收條件

Goal 可以**不經任何人確認就通過**，但只限每個條件都由主機判定時。條件要算「機器驗證」，它的 `verify` 必須是 `host_test`、指令**與專案設定的測試指令完全相同**、且期望的結束碼是 0（或未指定）。其他一切（不同的指令或選擇器、其他期望結束碼、`host_command`、`reviewer_check`、`manual`）都**由你判定**，不管測試套件多綠：套件通過只證明套件通過，不證明另一項需求成立。核准畫面會在你核准之前，逐條列出是主機還是你來判定。

執行結束時，Goal 執行會顯示對照表：每個最終條件由哪一次主機執行（指令、結束碼、git revision）或哪一位驗收的人判定；每個 Phase 的條件如何判定。模型自己說「做完了」永遠不算其中之一。

## 整個 Goal 共用一份預算

| 單位 | 計算方式 | 預設 |
|---|---|---|
| 嘗試 | 每個 Phase：該 Phase 的 Task 的開發者派工，含第一次 | 3 |
| Agent 派工 | **整個 Goal**：每個 Phase 的 Task 的每次 Provider 執行（任何角色，含備援與被中斷的）、每次 Delivery PM 分析、以及執行期間要求的每次修訂計畫 | 20 |
| 時間 | 整個 Goal：Phase 執行與最終驗證進行的時間。等待人與暫停不計；執行中電腦休眠則會計入（牆上時鐘） | 60 分鐘 |
| Token／金額 | **未知**：Provider 的命令列工具不會回報，頁面也如實標示 | |

預算在執行開始時凍結；修訂計畫不能提高它，開始新的 Phase 也不會拿到新的預算。它由資料庫列推導，所以當機不會讓計數出錯；並在工作開始處強制：每個 execution 在 `dispatch_agent`，每次 Delivery PM 分析或修訂計畫的要求則在記錄它的交易裡（`BEGIN IMMEDIATE`，所以兩個 runner 不可能同時拿到最後一份）。

## 狀態

`RUNNING` → `VERIFYING` → `PASSED`。途中：`WAITING_USER`（某個 Phase 或最終結果需要你；原因寫在頁面上）、`PAUSED`（你暫停）、`EXHAUSTED`（達到上限）、`FAILED`（某個 Phase 被取消，或沒有 Phase 能開始）、`CANCELLED`（你取消）。每次變化都是帶理由的事件；已結束的 Goal 執行、Phase 紀錄與驗證無法被修改或刪除（資料庫會拒絕）。有執行的 Goal 顯示的是執行的狀態；在那之前是 `READY`。

暫停會讓新工作不再開始（已在執行的步驟會做完，它交出的東西不會遺失）。恢復從停下的地方繼續，不增加預算；第二次恢復會被拒絕。停止整個 Goal 會結束進行中的 Phase 與其 Task；之後不會派任何工作，因為執行不在進行時就無法啟動 Phase。Goal 工作期間不能修改計畫；請先暫停。

## 它不會做的事

Commit、Push、Reset、Rebase、Release、Deploy 或 Publish。放寬 Provider 的權限。使用不受信任的 Agent Studio 角色或快照。接受不相容的契約變更。修改需求或驗收條件。執行模型或計畫提供的指令。超過任何上限。核准計畫。

## 已知限制

* **沒有使用過任何真實模型。** 以上都是用腳本化的 CLI 取代 Codex 與 Claude 示範的（真實的 adapter、真實的 worker、真實的 git 專案與真實的 Host Test，但沒有 Provider）。
* Windows、網路檔案系統、多台機器共用同一個 home 都未驗證；同一個 home 上的舊版 ccc-mcp 不受 Host Test 租約保護。
* 沒有控制台也沒有 `goal run-recover` 時，所有行程都中止的執行會一直等待。
* 一個 Goal 最多只有一次執行。已結束（通過、用盡上限、失敗或被停止）的執行不能再啟動；等待你處理的執行可以恢復。已結束的 Phase 不能在同一個 Goal 再跑，整合修正每個計畫版本最多一次。
* 時間是牆上時鐘：最終驗證進行中監督者被殺掉的話，那段時間在執行被重新接手前仍會持續計算。
* Phase／Goal 執行不支援 Classic Workflow，也不支援由瀏覽器中 ChatGPT 擔任的角色。
* 受保護路徑清單與最終檢查是防護，不是沙箱：請看 diff。
* 有 Goal 執行的專案，`clear_project_history` 與專案打包匯出會被拒絕。
