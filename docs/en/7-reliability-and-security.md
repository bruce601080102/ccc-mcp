# 7. Reliability and security boundaries

ccc-mcp treats an agent report as an input, not proof. Task state, source hashes, diffs, native CLI audit data, and host-executed test evidence are stored separately and drive completion.

## Reliability guarantees

- A committed context patch creates a durable pending-dispatch pointer before the next role runs. `task resume` retries that exact decision.
- A failing or zero-test host result prevents REVIEW from completing the task, even if the reviewer says no revision is needed. `brief.verification` (in `task status`/`task handoff`, rendered as text in `task show`) keeps this unambiguous: `agent_claim` (what the Agent itself reported — complete, needs revision, or no report yet) and `host_verification` (`passed`/`failed`/`no_tests_collected`/`not_executed`, from the host's own evidence) are always separate fields, and `reverted_due_to_host_failure` flags the specific case where host evidence — not REVIEW itself — sent the round back to SD/RD. `message` never calls an Agent's own claim a passing acceptance; that word is reserved for `host_verification: "passed"`.
- Quota exhaustion is classified separately from ordinary execution errors. Only the former may start one configured fallback; fallback loops are prevented.
- Context packages have a visible budget policy: optional Skill bodies, then compressible history, then a hard refusal to dispatch.
- A registered project's root directory cannot be silently lost: `project_access_events`/`context_versions`/`decisions` are append-only, so if the directory is deleted outside ccc-mcp, the next access recreates an empty, Git-initialized root instead of leaving the registration permanently stuck. The original files and Git history are not recoverable, but Context, tasks, and decisions remain intact in ccc-mcp's own database; the recovery is always recorded as a visible, SYSTEM-authored Context update (`context show`/`bootstrap_project`), never silent. A root that exists but resolves to a different path (tampering) is still rejected outright, never "repaired."
- `ccc-mcp project delete <id>` permanently retires a project ID: it disappears from `project list`, every later command refuses it, and the ID can never be registered again. It requires revoking any active project authorization first, refuses while an execution is still `QUEUED`/`RUNNING`, and needs the same interactive local confirmation as `authorize`/`revoke` (typing back `DELETE <id>` — in the terminal, or in the web console's own confirmation dialog, see [Web console](#web-console)). It never deletes files on disk (remove those yourself) and never deletes a row of Context/task/decision/evidence history — consistent with every other append-only table in this schema, it only records that the ID is retired. There is no undo.

## Meeting Mode

Off by default; `config meeting-mode on` inserts a bounded clarification round between SA's approved plan and SD/RD's first implementation attempt. Three guarantees:

- **Structural read-only.** The clarification-ask is a genuinely separate dispatch (role `SD/RD`, but requesting a `ClarificationRequest` rather than an `AgentReport`) — the CLI adapter's own sandbox flag (`codex --sandbox read-only` / Claude's `plan` permission mode) is set from that alone, and the worker never prepares a worktree for it. It is enforced the same way SA/REVIEW's read-only access always has been, not by asking the Agent nicely not to write.
- **`rounds_used` cannot be reset.** It is never a stored counter; it is always `COUNT(*)` over the immutable `meeting_clarifications` rows marked resolved, the same way context version and project access mode are derived from their own append-only tables elsewhere in this schema. A crash or retry can never grant extra rounds beyond the configured `max_rounds` (hard system cap 5).
- **`min_rounds` is enforced by prompt, not by failing the task.** Until that many rounds are resolved, SD/RD's check instruction says it MUST ask. If it still returns `no_blocking_question`, the workflow proceeds (no deadlock) and `clarification.gate.min_rounds_unmet` plus the Meeting Mode notice report it.

The gate fires at most once per task, immediately before SD/RD's first-ever implementation dispatch; once real implementation has started, a later REVIEW-requested revision never re-triggers it. Escalating to the PM (`pm_decision_required`) reuses the exact same `pending_dispatch` atomicity-and-resume machinery a normal `advance_project` round does — `resolve_clarification`'s decision and its next-dispatch pointer land in one transaction, so a crash immediately after is recovered by `resume_pending_dispatch` like any other interrupted dispatch.

When ChatGPT performs SA and/or SD/RD itself, the same exchange runs as interactive handoffs (`submit_clarification_request` / `submit_clarification_response`); the SD/RD check is still structurally read-only (no worktree, `write_task_file` refused) and the same rounds, `min_rounds` and escalation rules apply. One ChatGPT conversation then plays both sides, so treat the record as a structured self-check, not two independent opinions.

`meeting_mode.escalation` (`ask_user`, the default, or `auto_pm`) decides who is supposed to resolve a `pm_decision_required` round, and `clarification.triggered` tells the operator whether the gate ever actually produced a real question — but unlike the three guarantees above, neither is code-enforced. ccc-mcp has no way to verify from the backend whether the connected ChatGPT conversation actually asked the real human and waited for their reply, or decided on its own; `escalation` only shapes the wording `task_handoff` returns and the instructions the MCP server gives ChatGPT (see `interfaces/server.py`). Treat it as a strong operating convention, not a boundary ccc-mcp can enforce the way it enforces structural read-only access or `rounds_used`.

## MCP servers for agents

Agents run without MCP unless an operator runs `ccc-mcp skill install mcp <name>` — globally (no `--project`, every project) or with `--project <id>` for one project; only an explicit `--project` narrows the scope. The command is verified and recorded as an absolute path at install time; installation is possible only from the local CLI (no MCP tool, and `settings.json` is not an import source), and every provider can use it: Claude and Codex receive it as a launch-time configuration, ChatGPT through the `list_installed_mcp_tools` / `call_installed_mcp_tool` tools that ccc-mcp runs on its behalf, limited to the server+tool pairs the operator enabled. An installed MCP tool is not bound by a role's read-only file tools; it can do whatever that server allows, and Claude then runs without `--safe-mode` (see [Skills](6-skills.md#mcp-servers-let-dispatched-agents-call-a-local-mcp-live)). Treat installing an MCP as granting its tools to every role of every project it covers (all projects for a global install), including the ChatGPT PM.

## Authorization and execution

`project authorize` permits writes inside the registered project plus configured test execution. ccc-mcp may create a project venv and install dependencies found in `requirements.txt`, `pyproject.toml`, or `package.json`; package install hooks can execute code. Review dependency diffs.

Codex roles use OS-enforced `read-only` or `workspace-write` sandbox modes. Claude Code roles are restricted to selected tools and a worktree, but do **not** currently have the same OS-enforced boundary. Run ccc-mcp under a least-privileged OS account and do not represent Claude containment as verified sandboxing.

All project, task, and evidence paths are validated to resist traversal. Persisted evidence is checked by `ccc-mcp --project <id> verify`.

## Web console

`ccc-mcp authorize_project_local`/`deregister_project_local`/`clear_project_history_local` — the functions behind `project authorize`, `project delete`, and `clear-history` — have always required an interactive local terminal (`sys.stdin.isatty()`), and are never exposed to the MCP server, so neither a remote caller nor ChatGPT can trigger them. `ccc-mcp ui` is a fourth, local-only caller alongside the CLI and MCP server (same bridge, same core logic, see [9-protocol.md](9-protocol.md)); since it has no terminal to check, it establishes the same "a human, physically at this machine, deliberately chose this" guarantee a different way:

- The console binds `127.0.0.1` only — never a LAN or public address — regardless of any `--port` you pass.
- Each launch of `ccc-mcp ui` generates a fresh, random session token held only in that process's memory. It is handed to the browser once, in the URL fragment (`#token=...`), which browsers never send over the network or record in server logs; the page then holds it in `sessionStorage` for that tab only and attaches it as an `X-CCC-UI-Token` header on every API call. The token is never written to disk, never logged, and a fresh one is generated on every `ccc-mcp ui` restart.
- Every request to the console's API must present that exact token or it is refused (401) before touching any project. This is the web equivalent of the terminal's `isatty()` check: proof the caller is this specific locally-launched console, not an arbitrary HTTP client.
- `authorize`, `delete`, and `clear-history` additionally require typing back the same challenge text the terminal prompt uses (the project id, `DELETE <id>`, or `CLEAR HISTORY <id>`) in the browser dialog, verified again server-side — the same two-factor strength (session proof + typed acknowledgement) as the CLI's TTY check plus typed confirmation.
- Enabling write for a project is always a separate, explicit action with the consequences spelled out first (file writes, automatic test-command execution, that dependency installs can run package scripts) — whether that's the "Enable write" button on an already-registered project or the optional step inside "Add"/"Create". An existing read-only project is never upgraded as a side effect of viewing it.
- `revoke` needs no confirmation in either interface (reverting to read-only is always treated as safe) and is idempotent.

Everything else the console does — listing projects, task status, settings reads, dispatch-free config edits — reuses the exact same bridge methods `cli.py` and `interfaces/server.py` call, so it inherits the same path validation, symlink protection and append-only audit trail described above with no separate code path to drift out of sync.

**Connect and remembered runtime keys.** The console's Connect page is the same `admin tunnels get` → profile `init`/repair → `doctor --explain` → `tunnel-client run` sequence `ccc-mcp connect` has always run (`adapters/tunnel_client.prepare_tunnel_connection`, shared by both), supervised as a background subprocess instead of a foreground one so the page can show its live status and log. Opting in to "Remember this key on this device", explicitly saving a named profile, or using the CLI's `connect --remember` writes a runtime Secret Key to `<home>/tunnel/credentials.json`, `chmod 600` on POSIX — readable only by your OS account, not an additional encrypted vault. Several named profiles may hold different keys, even for one Tunnel ID; only one subprocess is active at a time. A key entered in the local page is sent to its token-protected localhost API, then used only as the `CONTROL_PLANE_API_KEY` environment variable of the `tunnel-client` subprocess. Saved keys are never echoed back to the browser; forgetting a profile deletes only that profile's record. Legacy CLI records remain readable.
