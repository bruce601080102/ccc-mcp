### 題目的刻意設計
- **分開提交狀態與驗收狀態**：Q09 把「有未 commit 變更」「主機測試通過」「待確認對應」拆成三個獨立欄位。「測試通過」不等於「可合併」，Q10 的 `not_a_reason` 會計為錯誤。
- **干擾項**：Q09 加入「匯出 CSV」，它不存在於任何 Task，所有格都應填「否」。這防止「全部填是」取得高分（全部填是只能得 18/21 左右，干擾項會把它拉下來）。
- **超出計畫以檔案為單位**：Q11 只問檔案，不要求把檔案歸屬到功能。`schema.sql` 沒有任何程式引用，無法確認它屬於哪個功能，因此不要求歸屬。

## 5. 計分規則

- 集合題（F1）：precision 與 recall 的調和平均；每個錯誤項算一條 FALSE 主張。
- Q09：每格 0 或 1。「是」「否」（或 JSON true / false）為作答。「不確定」與空白為不確定。其他文字列入 `invalid`，計為不確定，不計對錯。錯的格算 FALSE 主張。**Q09 正確率** = 正確格數 ÷ 21（不確定與無效計為不正確）。
- 空白（null）的清單題為未作答：0 分，計為不確定。「無」是明確答案：標準為空時得 1 分；標準非空時為 1 條 FALSE 主張。
- **Q10 有三個子分數**，各自 0 或 1，互不抵銷：
  - 答案：只有「不能」得分。
  - 阻擋原因：勾選的集合必須與標準完全相同。勾選「尚未 commit」一律算錯。測試通過不是阻擋的反面理由，也不是可合併的理由。
  - 待執行動作：勾選的集合必須與標準完全相同。勾選「需要重跑測試」或「不需要任何動作」一律算錯。
  - 每個錯誤勾選計為 1 條 FALSE 主張。不認識的選項列入 `invalid`，並計為錯誤。
- **Q10 正確率**（第 8 節第 3 項）= Q10 整題正確的比例（三個子分數全部正確）。各子分數的比例另外單獨報告，不設門檻。
- **Q10 錯誤理解率** = 錯誤子分數數量 ÷ 全部應答子分數數量（每題 3 個子分數）。留白與無效答案計為錯誤；`不確定` 不計為錯誤，另以不確定率單獨呈現。（T07 定義，第 9 節 STOP 使用此指標。）
- **危險誤判率** = 在存在未解除阻擋條件的 Q10 作答中，答「能」的比例。留白與 `不確定` 不計為危險誤判，但仍留在分母中。
- **整體正確率** = `score.py` 的 `score`（總得分 ÷ 總配分）。
- **Q10 整題正確**：答案、阻擋原因、待執行動作三個子分數全部正確（`q10_all_correct`）。
- **錯誤理解率** = FALSE 主張數 ÷ 全部主張數。
- **不確定率**：答「不確定」的題目數 ÷ 總題數，單獨列出，不算錯誤。
- **完成時間**：從顯示第一題到送出最後一題，中位數。單一區塊上限 15 分鐘，逾時未答的題目算 0 分。

## 6. 順序與學習效應

- 三案例構成同構，每個受試者依序看三個區塊；三區塊各用不同案例，條件順序與案例輪替要平衡。
- 完整平衡需要 **18 人**（6 種條件順序 × 3 種案例輪替）。初始 10 人是**驗收批次，不是完整平衡**，報告必須註明不平衡。
- 受試者不可回頭改答；不得在不同區塊之間交換材料。
- 不以 AI 協助作答。

## 7. 已知混淆（必須在報告中說明，不得忽略）

1. **產品視圖（A）的標籤混淆**：新手視圖把「尚未 commit」與「未確認」放在同一欄。這會影響 Q09 第一格的答題。此為**產品顯示問題**，需另行核准修改，本次未改動。
2. **待確認對應沒有附掛到功能**：新手視圖只在通知列出「1 組待確認」，沒有指出它屬於哪個功能；Q09 第三格由檔案成員關係推得，A 的受試者需要自行對應。
3. **超出計畫的歸屬缺口**：`schema.sql` 超出計畫，但產品只把超出計畫標在「標籤功能」上，沒有標在「本機儲存」上。Q09 不計此項，只在 Q11 以檔案為單位計分。
4. **B 組的撰寫者偏差**：B 由 Claude 依事實表撰寫，並非人類撰寫。在正式比較前必須替換。

## 9. ACCEPT、REVISE、STOP

- **ACCEPT**：第 8 節全部成立。只代表可以進入下一階段，不代表市場價值，也不代表真實專案中有效。
- **REVISE**：A 的整體正確率高於 B，但第 2、3、4、5 項任一未達標；或 kappa < 0.8，需重新編碼；或出現系統性混淆，例如常把修改誤判為新增。修正題目、材料或產品標籤後重測。
- **STOP**（任一成立即停止）：
  - A 的整體正確率不高於 B。
  - A 在 Q10 的錯誤理解率超過 15%，代表會導致錯誤的合併判斷。
  - 完成率低於 8 人。
  - A 的完成時間超過 B 的 1.5 倍，且正確率沒有提升。
  - 受試者平均求助次數超過 2 次。

## 11. 版本 2 變更（P0B 預試準備）

### 核准條件（已定義，見 `archgraph/gate.py`）
- **READY**：沒有阻擋項，且已 commit。
- **NEEDS_COMMIT**：沒有阻擋項，但尚未 commit。未 commit 是待執行的動作，不是阻擋。
- **BLOCKED**：至少一個阻擋項。阻擋項是 commit 不會修好的事實：主機測試未通過、超出計畫的檔案（本原型沒有接受機制，所以任何超出計畫的檔案都阻擋）、未確認的新舊對應、已規劃但未實作的內容。
- 因此「未 commit」與「不能合併」不等於。TASK-0003 的不能合併來自阻擋項，不來自未 commit。

### 材料變更
- 條件 A：頁首分開顯示「提交（Git）」、「驗證（主機測試）」、「核准條件」三項；未歸屬功能的超出計畫檔案顯示為專案層級警告，不隱藏；待確認對應可由兩端節點連到；前序 Task 的歷程保留在每個檔案的詳情與頁面表格中。
- 條件 C：每個 Task 的靜態頁面底部附該 Task 的事實表（可讀表格，不是 JSON）。
- 條件 B：內容未修改，只修正來源描述（v1.1）：為 Claude 根據完整事實表撰寫的固定文字基線，不是獨立 AI 摘要工具的輸出。

### 公平性檢查（`fairness_check.py`）
- 可找到性：每條必要事實在各條件中位於第一畫面（1）、需一步切換（2）、或僅在點擊後可見（3）。關鍵事實（阻擋項、超出計畫、依賴、待執行動作）必須在 2 以內。目前三組均為 1 或 2。
- 只替換領域詞：去除領域詞並排序清單後，三個案例完全相同。
- 污染：各案例不含其他案例的領域詞。
- **這不能消除學習效應**：結構相同意味著看過一個案例的人會更快回答下一個。控制方法是順序平衡與正式研究中的轉移檢查。

### 標準答案核對（`verify_keys.py`）
以獨立來源核對每條答案：git 的變更檔案（不使用 TaskDelta）、已核准計畫的檔案清單、重跑各 Task 的主機測試、import 陳述。三案例全部通過。
